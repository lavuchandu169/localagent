# Desktop app packaging (.dmg / .exe) — design spec

Date: 2026-08-29

## Purpose

Ship the first distributable beta of the localagent desktop app: a
`.dmg` for macOS and a `.exe` installer for Windows, built and
published automatically from CI. Today the app only runs from source
(`npm run electron`) — packaging/installers were explicitly out of
scope until now (README's "What's deliberately out of scope").

**Goal for this beta:** a working, downloadable installer on both
platforms, unsigned, distributed via GitHub Releases. Not in scope:
code signing/notarization, auto-update, a Linux target — all
deliberately deferred past this first beta.

## Tool: `electron-builder`

New devDependency. Handles both target formats (macOS `.dmg`, Windows
NSIS `.exe`) from one config, and is the de facto standard for
packaging Electron apps — actively maintained, well-documented, wide
adoption.

Rejected: `electron-forge` — equally capable, but `electron-builder`'s
config-only (no separate CLI scaffold/migration) approach fits better
on top of an already-established project structure than adopting
forge's own project conventions would.

## Config

Lives directly in `package.json` under a new `build` key — matches
this project's existing lean, single-file convention (no separate
`electron-builder.yml`).

```jsonc
"build": {
  "appId": "com.chandulavu.localagent",
  "productName": "localagent",
  "directories": {
    "output": "release"
  },
  "files": [
    "dist/**/*",
    "package.json"
  ],
  "asarUnpack": [
    "**/*.node"
  ],
  "mac": {
    "category": "public.app-category.developer-tools",
    "icon": "src/electron/renderer/icon-512.png",
    "target": [
      { "target": "dmg", "arch": ["arm64", "x64"] }
    ]
  },
  "win": {
    "icon": "src/electron/renderer/icon-512.png",
    "target": [
      { "target": "nsis", "arch": ["x64"] }
    ]
  },
  "publish": {
    "provider": "github"
  }
}
```

**Revised after initial ship:** the `mac.target` array above shipped
with both `arm64` and `x64`, but the final whole-branch review caught
that the x64 target was silently broken. `@node-llama-cpp/mac-x64` is
an npm `optionalDependency` gated on `cpu: ["x64"]`; on an arm64
machine — including GitHub's `macos-latest` CI runners, which are also
Apple Silicon — `npm ci`/`npm install` never installs that variant, so
electron-builder builds the x64 target from an arm64-only
`node_modules`, embedding arm64-compiled native addons
(`@node-llama-cpp/mac-arm64-metal`, `@reflink/reflink-darwin-arm64`)
inside an x64 Electron shell. The result would not launch correctly on
real Intel hardware, and this wasn't a local-only artifact — CI would
have reproduced it identically. `mac.target.arch` is now `["arm64"]`
only; Intel Mac support is a deliberate scope cut for this beta,
deferred to a future release, and documented in the README rather than
silently shipped broken.

### The output-directory collision

electron-builder defaults its output folder to `dist/` — the same
directory the existing `tsc` build already writes the compiled app to
(`npm run build` → `dist/electron/main.js`, etc., which packaging then
needs to read *as input*). Left at the default, a packaging run would
write its own output into the same tree it's reading from mid-build.
`directories.output: "release"` puts packaged artifacts in a separate
`release/` folder instead, gitignored alongside `dist/`.

### Native modules (`node-llama-cpp`)

`node-llama-cpp` ships prebuilt native binaries (`.node` files) that
cannot execute from inside an `.asar` archive (Electron's default
app-bundling format — a single-file virtual filesystem that native
addons can't be `dlopen`'d from). `asarUnpack: ["**/*.node"]` keeps
those specific files as real files on disk within the packaged app
instead of inside the archive, while everything else still gets
archived normally.

### Icons

Both platforms' icon formats (`.icns` for macOS, `.ico` for Windows)
are auto-generated by electron-builder from the single source PNG
already in the repo (`src/electron/renderer/icon-512.png`, 512×512).
512×512 is sufficient for a working icon at every size electron-builder
generates; a future 1024×1024 source would look marginally crisper at
the largest display sizes but isn't a blocker for a beta.

## Versioning

`package.json`'s `version` field changes from `0.1.0` to
`0.1.0-beta.1` — electron-builder names every artifact directly from
this field (e.g. `localagent-0.1.0-beta.1-arm64.dmg`,
`localagent-0.1.0-beta.1-x64.exe`), and it's also literally what
"first beta" means for this release.

## Local build scripts

Three new `package.json` scripts, for building/testing without
pushing a CI tag:

```jsonc
"package:mac": "npm run build && electron-builder --mac",
"package:win": "npm run build && electron-builder --win",
"package:all": "npm run build && electron-builder -mw"
```

`package:win` only produces a genuinely usable, testable `.exe` when
run on an actual Windows machine (or in CI's `windows-latest` runner)
— electron-builder can technically attempt a Windows cross-build from
macOS/Linux via Wine, but that path is unreliable and not something
this spec relies on. `package:mac` is expected to be built and
verified directly in this repo's own macOS environment before ever
cutting a release.

## CI: `.github/workflows/release.yml`

Triggered on pushing a tag matching `v*` (e.g. `v0.1.0-beta.1`). Two
parallel jobs:

- **`build-mac`** (`macos-latest`): checkout → setup Node → `npm ci` →
  `npm run package:mac` → electron-builder publishes the resulting
  `.dmg`s straight to a GitHub Release matching the pushed tag (via
  `--publish always`, using electron-builder's built-in GitHub
  integration and the `GITHUB_TOKEN` GitHub Actions already provides —
  no new secret needed since builds are unsigned).
- **`build-win`** (`windows-latest`): same shape, `npm run package:win`,
  publishing the `.exe`.

Both jobs publish to the *same* Release (electron-builder's GitHub
publisher creates the release on first upload if it doesn't exist yet,
and appends assets to it on subsequent uploads for the same tag) — so
a single tag push ends with one Release carrying both platforms'
installers.

## What happens for users (unsigned builds)

- **macOS**: Gatekeeper blocks the unsigned app on first open
  ("cannot be opened because the developer cannot be verified"). Users
  right-click the app → **Open** → confirm in the dialog, once. README
  gets a short note on this.
- **Windows**: SmartScreen shows "Windows protected your PC." Users
  click **More info** → **Run anyway**, once. Same README treatment.

Both are standard, expected friction for an unsigned beta — not bugs,
not blockers for this release.

## Testing

No automated test framework coverage — packaging is inherently an
integration concern (real OS-level app bundling), matching how this
project already treats other Electron-only code (`main.ts`,
`preload.cjs`) with manual/live verification instead of unit tests.
Verification for this spec:

- `npm run package:mac` run directly in this environment, producing a
  real `.dmg`; mounted and the app launched from it, confirming the
  packaged app actually starts (workspace picker renders, a task can
  run) — not just that the build command exits 0.
- The GitHub Actions workflow itself is verified live by pushing an
  actual beta tag and confirming both jobs succeed and a Release with
  both artifacts appears — not just read for correctness.

## Out of scope for this beta

- Code signing / notarization (macOS) and a code-signing certificate
  (Windows) — real cost and process, deferred past this first beta.
- Auto-update (`electron-updater`) — no mechanism for the app to
  notice or install a newer release; every future update is a fresh
  manual download for now.
- Linux packaging (AppImage/deb/etc.) — not requested.
- Release notes automation beyond electron-builder's default GitHub
  Release creation (no changelog generation).
